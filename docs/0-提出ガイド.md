# バックエンド採用試験提出ガイド

## 概要

このチャレンジでは、バグのあるRailsアプリケーションを修正・改善する必要があります。
アプリは複数のテナント（組織・サイト）が記事を投稿する**マルチテナントのブログシステム**を想定したもので、Users・Posts・Commentsを持ちます。
ただし**現状はテナント分離が一切考慮されておらず、全テナントが単一の共通DB（共通テーブル）を共有しています**。意図的なバグ・不足している機能に加え、こうした設計上の課題も解決の対象です（マルチテナントDBの取り扱いは第8問を参照）。

## 前提環境

回答にあたっては、以下のツールがローカルに用意されていることを前提とします（バージョンは目安です）。

- **Docker / Docker Compose**：アプリと**MySQL 8.0**の起動・実行に使用します（`docker compose up`）。原則としてコンテナー内（`docker compose exec app bash`）での開発を想定しています。
- **Git**：ブランチ運用・PR作成に使用します。
- **エディター**：**VS Code**を推奨します（`Dev Containers`拡張の利用も可）。任意のエディターで問題ありません。
- **Ruby / Rails**：ローカルにRuby環境を用意する場合は`.ruby-version`（**Ruby 3.4.x**）および`application/Gemfile`を参照してください。

> これら以外のツール（ベンチ計測ツール、プロファイラ等）を前提とする回答を行う場合は、使用ツールと前提を該当する `notes/<問題番号>-*.md` に明記してください。

## 開始方法

1. このリポジトリをテンプレートとして、ご自身のGitHubアカウントの `public` リポジトリで、`{任意名}-backend-hiring-challenge` の名前でリポジトリを作成してください。
2. リポジトリの作成が完了しましたら、応募媒体の機能にて、弊社採用担当に**作成したリポジトリの閲覧用URL**を送付ください。
3. 各問題は当リポジトリの `docs/` 以下に格納してあります。内容を確認してください。
   - この時点ではまだ「試験開始」とはなりません。
   - 不明点がある場合は、**ご自身のリポジトリの `Issue`** に質問を記載してください。
4. 質疑応答が完了し、着手する準備が整いましたら、応募媒体の機能にて、**「試験開始」**の旨を弊社採用担当にお知らせください。
5. `application/` ディレクトリに移動
6. `docker compose up` を実行してアプリとデータベースを起動
7. アプリは `http://localhost:3000` で利用可能
8. `docker compose exec app bash` を使用してコンテナーに入り開発

## 要件
`docs/`ディレクトリに記載された全20問（第1問〜第20問）を対象とします。各問題には具体的な要件と受け入れ基準があります。

### 取り組み方針

- 全20問は**ボリュームのあるセット**です。期間内にすべてを同じ深さで仕上げることは前提としていません。
- **何を優先し、何を後回し（または見送り）にするかの判断も、評価対象です。** 限られた時間で本質的な改善に時間を割けるかを見ます。
- 取り組まなかった項目、深く掘れなかった項目について、**「やらなかった理由・残課題」をPR説明または該当問の `notes/` に残してください**（判断の根拠を残すことが重要）。
- 各問題内に「追加要件」セクションがある場合、本体要件＋追加要件のうち、限られた時間で何を取捨選択したかも判断材料です。

### 提出物の置き場所

- 各問の作業記録・計測結果は、原則 `notes/<問題番号>-*.md` に書いてください（`notes/_TEMPLATE.md`を参考に）。
- 計測・再現が求められる問題（ベンチ、プロファイル、EXPLAIN、並行実行の最終状態、イメージサイズ等）は、**自分の環境での実測値・証跡**を残せると説得力が増します。

## 提出

**提出は「設問（問題）単位」のPull Requestで行ってください。** 1つのPRに複数問の変更をまとめたり、全問を1本のPRにまとめることは避けてください（レビュー観点が混在し、評価が困難になります）。

1. **問題ごとに**専用の`feature`ブランチを作成する（例：`feature/8-schema-index`）。各問題文の冒頭にある「`feature`ブランチとして作成してください」の指示に沿ってください。
2. その問題の修正を実装し、**問題ごとに1つのPR**として提出する。
   - PRのタイトル・説明に、対象の問題番号、実装内容、判断・トレードオフ、未対応事項（あれば）を記載してください。
   - 前の問題の解答を踏まえる必要がある場合は、前の課題のブランチから派生させて次の課題のブランチを作成する**featureブランチのネスト**を許可します（FAQ参照）。
3. すべてのテストが通ることを確認（RSpec、RuboCop、Reekを必要に応じて追加）。
4. 明確なコミットメッセージで変更をコミットする。
5. 受験が完了しましたら、応募媒体の機能にて、弊社採用担当にお知らせください。

## 評価基準

- コード品質と可読性
- Rails規約の適切な使用
- パフォーマンス最適化
- セキュリティベストプラクティス
- テストカバレッジ
- データベースクエリの効率性
- エラーハンドリング
- API設計

## 時間見積もり

推奨期間：試験開始の宣言から**20日以内**（ご自身のペースで取り組んでいただけます）。
全20問にどこまで時間を割くかも判断材料です。完答が前提ではなく、**優先順位の付け方と取捨選択の説明**を評価します。

- 本番環境対応のコードに焦点
- 仮定した点は文書化
