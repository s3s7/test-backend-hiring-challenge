# 第19問：監査ログの追記専用設計（イベント記録と状態再構築）

下記要件を満たす`Pull Request`を`feature`ブランチとして作成してください。

## 背景

本アプリは将来、外部監査やコンプライアンス対応の対象になる可能性があります。「誰が・いつ・何を変更したか」を、**事後に書き換えられない形**で残す必要があります。

本問では、業務テーブル（`users` / `posts` / `comments`）の**現在値（ステート）とは独立した、追記専用のイベント記録**として監査ログを設計します。業務テーブルは検索性のために残しますが、**監査ログ単体から論理状態を再構築できる**ことを目指します（イベントソーシング的なアプローチ）。

第10問（認証・認可）、第14問（冪等API）、第16問（矛盾仕様の調停＝退会と匿名化）と相互に関係します。整合を取って設計してください。

## 要件

1. **追記専用の監査ログテーブル**を設計・実装する。
   - 監査対象イベントは少なくとも以下を含めること：
     - `User`：作成・更新・退会
     - `Post`：作成・更新・公開・論理削除
     - `Comment`：作成・更新・承認・削除
   - 1レコードに含むべき最低限の情報：actor（操作者）/ 対象（type, id）/ 操作種別 / 発生時刻 / 変更前後の差分または十分な再構築情報 / リクエスト相関ID（第11問の構造化ログと突き合わせ可能であること）。
   - **UPDATE / DELETE をDB側で禁止**すること。アプリ層のガードのみでは不可（例：BEFORE UPDATE / BEFORE DELETE トリガでの拒否、ロール権限の分離、CHECK制約による論理ロックなど、選択した手段の理由を `notes/19-audit-log.md` に書く）。

2. **業務テーブル変更と監査ログ書き込みの原子性**を担保する。
   - 業務テーブル更新と監査ログ書き込みは**同一トランザクション**で成功・失敗すること。片方だけがコミットされる状況（dual-write）を排除する。
   - `after_commit` の別接続で書く実装が抱える落とし穴（プロセスクラッシュ・コミット直後の死活）を `notes/19-audit-log.md` に短く触れること。

3. **状態の再構築**を可能にする。
   - 監査ログのみを入力として、ある時点（タイムスタンプ指定）の `posts` / `comments` の論理状態を**再生するクエリまたはRakeタスク**を1つ実装する。
   - 業務テーブルを空にした状態でも、監査ログから対象時点の状態が一致することを**テスト**で示すこと（差分はキー集合と主要カラムで比較すれば十分）。

4. **個人情報の削除要件との両立**（第16問と連動）。
   - 退会ユーザーの個人情報（氏名・メール等のPII）を**速やかに匿名化／削除**する要件と、監査ログの**不変性**は直接衝突する。
   - 採用する解決方針を**複数案比較**して `notes/19-audit-log.md` に書き、1案を実装すること。比較対象の例：
     - **crypto-shredding**：PIIを暗号化して保存し、鍵を破棄することで実質削除。
     - **PII分離**：監査ログ本体には参照IDのみを保存し、PIIは別テーブル／別ストアに置いて削除可能にする。
     - **匿名化ペイロード**：書き込み時点でハッシュ化／マスクして保存する（後から元に戻せない）。
   - **「監査ログを削除する」「該当列だけ UPDATE で消す」は不変性を壊すため不正解**とする。

5. **改ざんしにくさの工夫（任意・加点）**。
   - 直前レコードのハッシュを次レコードに含める（ハッシュチェーン）、署名、外部追記ストレージへの定期エクスポート等のいずれか1つを採用してよい。
   - 採用する場合、**並行挿入下でチェーンの順序が壊れない**ことを検証すること（シリアライズ手段の選定理由を含める）。
   - 時間が無ければ見送ってよい。見送り理由を書けば減点しない。

6. **パフォーマンスと運用**。
   - 監査ログは時間とともに巨大化する。インデックス設計（典型は `(target_type, target_id, occurred_at)` と `(actor_id, occurred_at)`）と、保持期間／アーカイブの方針を `notes/19-audit-log.md` に記載すること。
   - 監査ログ書き込みが業務トランザクションのレイテンシに与える影響を1ケースでよいので**計測**し、数値を残すこと（マイクロベンチで可）。

## 受け入れ基準

- 監査ログテーブルが**DB側で追記専用**になっている（UPDATE / DELETE がブロックされ、テストで阻止が確認できる）。
- 業務テーブルの更新と監査ログ記録が**同一トランザクション**で原子的に行われる（片方だけ残らないことをテストで確認できる）。
- 監査ログのみから、対象時点の `posts` / `comments` の状態が**再構築できる**こと。
- 退会ユーザーの個人情報を匿名化／削除しても、監査ログの**不変性が破られない**こと（採用方針が明文化され、実装と一致していること）。
- `notes/19-audit-log.md` に **再現・原因・対応・判断・証跡**（テンプレート参照）が記載されていること。

## ヒント（取り組み順の例）

- まず（要件1）のスキーマと書き込みポイントを決め、業務操作のうち代表1つ（例：`Post#publish`）で end-to-end の流れを通す。
- 次に（要件2）の原子性、（要件3）の再構築を、その1操作で動かす。
- そのあと対象イベントを広げ、（要件4）PIIとの両立、（要件6）インデックスと計測を進める。
- （要件5）は時間が余ったときに着手する。

> AIを使う場合：「append-onlyの監査ログを作って」と一言で頼むと、典型的な `audit_logs` テーブル（id, user, action, payload, created_at）が出てくるだけで、**DB側の不変性担保・同一トランザクション・状態再構築・PII匿名化との両立**は満たされません。生成物を**そのまま使わず**、各要件と突き合わせて足りない部分を自分で設計してください。
