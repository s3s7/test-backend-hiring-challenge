# 第13問：並行性とデータ競合（カウンター競合・デッドロック）

下記要件を満たす`Pull Request`を`feature`ブランチとして作成してください。

## 背景

`posts`には`views_count`カラムがあり、投稿の表示（`GET /posts/:id`）のたびに加算しています。
また、投稿の公開（`PATCH /posts/:id/publish`）とコメントの承認（`PATCH /comments/:id/approve`）は、それぞれ行ロックを取りながら関連レコードを更新します。
これらは単体リクエストでは正しく動きますが、**並行アクセス時に正しさが崩れます。**

## 要件

1. **カウンター競合（ロストアップデート）の解消**
   - `views_count`の加算が、同時に多数のリクエストが来ても**必ず正確な回数**になるよう実装し直す。
   - 「なぜ現状の実装が並行下で値を取りこぼすのか」をInnoDBの動作（行ロック・Read-Modify-Write）に触れて`notes/13-concurrency.md`に説明する。
2. **デッドロックの再現と解消**
   - `publish`と`approve`を同一の投稿・コメントに対して並行実行し、**デッドロックを再現**する。
   - `SHOW ENGINE INNODB STATUS`等のデッドロックログを採取し、`notes/13-concurrency.md`に添付する。
   - ロック獲得順序を統一する等の方針でデッドロックを解消する。
3. 上記いずれも、競合を**再現する検証スクリプト/テスト**を同梱すること（例：N並列で`show`を叩き最終`views_count`を検証）。

## 受け入れ基準

- N並列アクセス後の`views_count`が必ず正確値（=リクエスト数）になることが検証できること。
- デッドロックの再現ログと、解消後に再現しないことの証跡があること。
- 競合が起きる理由と採用した解決策が`notes/13-concurrency.md`に説明されていること。

> 補足：単に`transaction`で囲うだけ、`validates`を足すだけでは不十分です。なぜその対策が並行下で正しいのかを説明できる状態を求めます。
